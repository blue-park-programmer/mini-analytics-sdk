## B. 6단계: 단건 격리 (설계 §6.4, R-8'')

### 동작
```
배치(여러 건) 400/422 → 그 배치의 마지막 id까지 "격리 대상"으로 정함. 아무것도 삭제하지 않음
  └ 격리 대상을 한 건씩 전송 (같은 전송 루프, 재귀 없음)
      ├ 2xx                                → 그 건만 삭제 (정상 전달)
      ├ 400/422 + {"error":{"code":"invalid_event","messageId":"<보낸 id>"}}
      │   └ 이번 프로세스 삭제 < 20          → 그 건만 삭제, rejectedByServer +1
      ├ 400/422 그 밖 (코드 없음, 다른 코드, messageId 불일치, HTML, 20건 상한 도달)
      │   └ 서버/요청/계약 문제로 판단        → 삭제 없음, 격리 종료, 최대 backoff(5분), Log.e
      ├ 5xx / 네트워크 / 429 / 401 / 403    → 격리 상태 유지, 해당 backoff
      └ 413                                → 그 건 삭제 (기존 규칙)
  └ 격리 경계보다 id가 큰 이벤트(격리 중 새로 저장됨)는 격리가 끝난 뒤 다시 배치로 전송
```
- 추가된 상태: `isolateThroughId`(경계)와 `rejectionDeletes`(프로세스당 삭제 수) **두 개**뿐입니다(R-8''). 둘 다 메모리에만 둡니다.

### 사용자 지정 검증 조건
| 조건 | 검증 | 결과 |
|---|---|---|
| 배치 400/422만으로는 삭제하지 않음 | 배치 400의 본문에 `invalid_event`가 있어도, 여러 건 요청에 대한 응답은 근거가 되지 않음 → 삭제 0건 | 통과 |
| 계약상 영구적으로 유효하지 않다고 판단할 수 있을 때만 삭제 | 단건 요청에 `invalid_event` 코드가 있고 `messageId`가 일치할 때만 삭제 | 통과 |
| 요청 형식, 인증, 계약이 잘못된 경우 보존 | 근거 없는 400 5종(본문 없음, HTML, 다른 코드, messageId 불일치, messageId 없음) / 401 / 계약 없는 서버(전부 HTML 400) → 모두 삭제 0건 | 통과 |
| 무한 재귀와 과도한 요청 방지 | 재귀 없이 같은 루프에서 처리. 격리 한 번에 단건은 최대 배치 크기(100건 배치 → 정확히 1 + 100번). 근거 없는 400이면 첫 단건에서 멈춤 → 계약 없는 서버에는 **1시간에 요청 24번 이하**, 이벤트 100건 보존, error 로그 2번 이하 | 통과 |
| 섞인 배치에서 정상 이벤트 보존 | 5건 중 1건만 잘못됨 → 정상 4건 모두 전달되고 1건만 삭제. 격리 중 새로 저장된 이벤트는 격리 후 배치로 전송 | 통과 |
| 일부만 저장하는 서버의 계약과 멱등성 문서화 | 설계 §6.5에 표로 정리 (아래 C) | 문서화 |

### 그 밖의 격리 테스트
- 422는 400과 같이 처리됨
- 한 건짜리 배치에 근거가 있으면 바로 삭제됨
- 격리 중 503 → 네트워크 오류 → `429 Retry-After` → 성공: 격리 상태를 유지한 채 backoff를 따름
- 격리 중 401: 격리 상태를 유지하고 5분 뒤 이어서 진행
- 버그가 있는 서버(모든 단건에 `invalid_event`): **20건만** 삭제하고 나머지 10건 보존. 그 뒤로도 더 지우지 않음
- 격리 중 재시작: 다시 격리하되, 이미 전달된 이벤트는 다시 보내지 않음
- 격리 대상이 상한 정리로 지워진 경우: 격리가 자동으로 끝남

## C. 일부 저장 서버의 계약과 멱등성 (설계 §6.5)
| 서버 상황 | 서버가 보내야 하는 응답 | SDK | 서버의 책임 |
|---|---|---|---|
| 일부가 영구적으로 잘못되고 나머지는 저장함 | 2xx + `rejected` | 배치 전체 삭제, 거부 수 집계 | — |
| 일부만 저장한 뒤 장애 | 5xx 또는 연결 종료 | 배치 **전체**를 같은 `messageId`로 재전송 | `messageId` 중복 제거 |
| 요청 자체를 해석할 수 없음 | 400/422 (`invalid_event`가 아닌 응답) | 격리 → 근거 없으면 보존 | — |
| 한 건짜리 요청의 이벤트가 잘못됨 | 400/422 + `invalid_event` + messageId | 그 건만 삭제 (프로세스당 20건까지) | — |

- **SDK가 감지할 수 없는 계약 위반**이 있습니다. 서버가 일부만 저장하고 `rejected` 없이 2xx를 돌려주면, 저장되지 않은 이벤트는 조용히 유실됩니다.
- 서버가 `messageId` 중복 제거를 하지 않으면, 응답 유실이나 일부 저장 + 5xx 때 같은 이벤트가 **중복 저장**됩니다. 이 위험을 e2e 테스트로 직접 확인했습니다(아래).

## D. Contract Mock Server (테스트 전용)
- 위치: `src/test/.../mockserver/ContractMockServer.kt` (MockWebServer 기반). **배포물(AAR)에는 포함되지 않습니다** (확인함). 운영 서버 구현이 아닙니다.
- 구현한 계약: 인증(`Authorization`), 요청 파싱, `messageId` 중복 제거(끌 수 있음), identify 쌍 단위 멱등, 2xx + `rejected`
- 서버 모드: `CONTRACT`, `BATCH_400`, `BROKEN_400`
- 주입할 수 있는 장애: "저장 후 응답 유실", "앞 절반만 저장 후 503"

**SDK 전체 경로 e2e 테스트 9개** (실제 `HttpUrlConnectionTransport` + 실제 dispatcher + 실제 소켓):
| 테스트 | 확인 내용 |
|---|---|
| 정상 경로 | track·identify 4건이 순서대로 한 번씩 저장되고 로컬에서 삭제됨, 연결 1건 |
| 응답 유실 | 요청 2번, 도착 6번(3건 × 2), **저장은 3건** |
| 일부 저장 + 503 | 요청 2번, 도착 8번, **저장은 4건** |
| **중복 제거하지 않는 서버** | 같은 이벤트가 **2번 이상 저장됨**. 문서화한 위험을 그대로 재현 |
| 반복 identify | 메시지 2개(서로 다른 messageId), 연결은 1번 |
| 계약 서버의 `rejected` | 요청 1번으로 처리 완료, 정상 2건 저장, 거부 1건 집계 |
| 배치 400 서버 | 요청 1 + 5번, 정상 4건이 순서대로 저장, 잘못된 1건 삭제 |
| 계약 없는 400 서버 | 여러 번 시도해도 3건 보존, 삭제 0건 |
| 잘못된 apiKey | 401, 2건 보존 |

## 진행 중 발생한 문제와 조치 (숨기지 않고 기록)
1. **e2e 테스트가 간헐적으로 실패함 (테스트 경합)**
   - Uploader의 "시작 시 1회 확인"(설계 §4.4)이 `track()`의 commit과 경합해서, 배치 구성이 실행할 때마다 달라졌습니다. 그래서 격리 경로가 실행되지 않거나, 테스트가 기다리던 상태를 관찰하지 못했습니다. SDK 동작은 설계대로였습니다.
   - 이벤트를 "이전 실행이 남긴 이벤트"로 미리 저장한 뒤 클라이언트를 시작하도록 바꿔서, 한 배치로 보내지는 것을 결정적으로 보장했습니다. 그리고 요청 수를 단언해서 격리와 일부 저장 경로가 **실제로 실행되었음**을 증명합니다. 수정 후 10번 반복해서 10번 모두 통과했습니다.
2. **mutation check 실행이 30분 이상 멈춤**
   - M1 결함 때문에 한 테스트의 assertion이 실패했는데, 그 테스트는 반복문 안에서 만든 scope를 정리하지 못했습니다. 남은 무한 ticker가 `runTest`의 마무리 단계에서 가상 시간을 끝없이 진행시켰습니다(스레드 덤프로 확인).
   - 멈춘 실행을 종료하고, **mutation이 남아 있던 `Uploader.kt`를 백업에서 복원**했습니다(diff로 확인). 해당 테스트도 다른 helper와 같은 방식(`backgroundScope`에 등록, `finally`에서 취소)으로 고쳤습니다. 같은 패턴의 테스트는 이것 하나뿐임을 확인했습니다.
3. **로그 억제가 처음에는 동작하지 않음**: 격리 시작과 서버 문제 판단이 번갈아 발생하면서 "마지막 실패 종류"가 계속 바뀌었습니다. 실패 종류별로 따로 기록하도록 고쳤습니다.
