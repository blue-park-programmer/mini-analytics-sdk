# v1 성능 벤치마크 보고서 (Step 8)

- 작성일: 2026-11-16
- 기준: `main` `9178890` 이후의 SDK. §1~§8의 측정은 SDK 변경 없이 했고(측정 코드만 추가: `benchmark-host/`, `benchmark/`, `tools/benchmark/`), §10은 배경 CPU 최적화 1~3을 적용한 전후 비교다.

### 3.3 간헐 호출: 사실과 가설
| 구분 | 내용 |
|---|---|
| **사실** | 간헐 호출은 몰아서 호출할 때보다 수십~백 배 느리다(백그라운드 p50 0.43~0.76ms, 메인 0.46~0.81ms). 간격이 길수록 느려지는 경향이 있다 |
| **사실** | SDK를 부르지 않는 대조군도 같은 조건에서 p50 0.12~0.21ms, p99 0.36~0.83ms였다. 기기 자체가 대기에서 깨어나는 영향이 크다. 그래도 SDK 호출은 대조군의 약 3~4배였다(p50 차이 약 0.34~0.60ms) |
| **사실** | 느린 호출 동안 호출 스레드는 p50 기준 계속 실행 중이었다(CPU 시간 ≈ 경과 시간). anim에서는 p99에 실행되지 않은 시간이 1~2ms 섞였다 |
| **사실** | **UI가 동작할 때(anim) 호출이 더 빨라지지 않았다.** idle보다 p50이 약 17~29% 높고 p99는 약 1.9~2.7배였다 |
| **사실** | anim에서 프레임 기준(16.7ms) 초과는 SDK·대조군 모두 실행당 0~2개(약 3,000~3,600개 중)로 차이가 보이지 않았다. 이는 이 조건(60Hz, 100~500ms마다 1건)의 관찰이며 프레임 영향의 최종 판단은 Macrobenchmark에서 한다 |

| 가설 | 대기 뒤 CPU 클록 저하·캐시가 비는 효과가 대조군과 SDK를 모두 느리게 한다(클록·저전력 상태는 루팅 없이 측정할 수 없었다) |

## 4. pos0·간헐 호출 비용의 위치 (simpleperf)
profileable release(AOT), 백그라운드 100ms 간헐 호출, `simpleperf record --app` cpu-clock 20kHz 콜스택, 30초(약 300회). R8 mapping으로 이름을 되돌림(R8이 합친 이름은 호출 경로 위치로 판단).

| 호출 스레드 track() 안 경로 | 비중 |
|---|---|
| `EventPipeline.enqueue` → `Channel.trySend` → 쉬고 있던 저장 coroutine 재개 → `LimitedDispatcher`/`CoroutineScheduler.dispatch` → `tryUnpark` → `LockSupport.unpark` → `syscall` | 약 38% (그중 unpark·syscall 약 17%) |
| `UUID.randomUUID`(→ `SecureRandom.nextBytes`) | 약 21% |
| `UUID.toString` | 약 13% |
| 그 밖(속성 정리, 할당, lock, 인터프리터 일부) | 약 28% |

- **사실(이 조건의 300회 집계)**: 간헐 호출에서 호출 스레드 CPU의 가장 큰 부분은 저장 coroutine을 깨우는 경로와 messageId(UUID) 생성이다.
- **가설(유력, 미확정)**: normal의 pos0 비용도 같은 경로다. 근거: 코드상 pos0는 저장 coroutine이 쉬고 있을 때 이 경로를 탄다, 직전 호출 1건(prewake)이 비용을 흡수했다(pos0 p99 123→34µs), CPU 시간 ≈ 경과 시간. pos0 자체를 프로파일하지는 않았다.
- **한계**: 샘플링 주기(50µs)가 호출 길이와 비슷해 개별 호출이 아니라 집계 비율만 얻었다. 커널 기호가 막혀 syscall 내부는 보이지 않는다. 프로파일러 오버헤드로 절대 시간은 부풀려진다(비율만 유효). AOT 상태에서만 수집했다.

## 5. SQLite 저장 처리량·commit 지연 (2026-11-16)
release, 시나리오당 5회, 순서 섞음, 실행마다 새 프로세스. 열 상태 0, 배터리 29.9~31.1℃.

### 5.1 메커니즘 분리와 독립 검증
각 시나리오는 저장 손실 메커니즘이 하나만 일어나도록 설계했고, 모든 이벤트에 순번(seq)을 넣어 **측정 뒤 DB와 업로드 서버 양쪽에서** 확인했다.

| 시나리오 | 설계 | DB 결과 (5회) | 서버 결과 (5회) | 판정 |
|---|---|---|---|---|
| store_burst | 대기 명령 < 1,000, 총 4,650 < 상한 10,000 | 4,650/4,650, 누락 0 | 4,650 고유, 누락 0 | 저장 = 호출 (손실 없음) |
| store_sparse_cpu | 100ms마다 300건 | 300/300 | 300 고유 | 손실 없음 |
| store_evict | 상한 1,000, 900건 × 3묶음(+장벽) | 1,000행, **앞부분 1,700 누락**, 중간 0 | 1,000 고유, seq 1,700~2,699 | **DB 상한 정리만** (오래된 행부터) |
| store_drop | 상한 10,000, 5,000건 연속 | 1,356~1,571행, 앞부분 0, **중간 3,429~3,644 누락** | DB와 같음 | **메모리 큐 폐기만** |

- 25회 모두 DB 행 수 = 서버 고유 수, 업로드 뒤 남은 행 0. store_evict는 측정 중 업로드 시도(503 2~4회)를 서버가 거부했고 업로드 단계에서 모두 전달됐다.

| 묶음(900건) 저장 시 배경 CPU/건 | 0.09ms (0.06–0.10) |

- 사실: 간헐 호출(이벤트마다 트랜잭션 1개)에서는 배경 CPU가 **이벤트당 수 ms**로, 묶음 저장의 약 50배다. 100ms마다 1건이면 한 코어의 약 5%에 해당한다.
- §4 프로파일(같은 조건)의 배경 스레드 구성: commit·상한 정리(개수 조회 `simpleQueryForLong` 약 22~26%, 트랜잭션 commit `ioctl` 등 약 30%), commit 뒤 `counts()` 16.5%, `SimpleDateFormat` 약 10%. 배경 CPU는 `/proc/self/task/*/schedstat`의 호출 스레드 외 합이며 메인 스레드(콜백 처리)도 포함한다.

## 6. 측정 신뢰성과 한계
- 기기 1대, CPU 클록 고정 불가(루팅 없음). 앱 화면은 60Hz로 동작했다(기기 최대 120Hz 조건은 측정하지 않음).
- p99는 실행 간 편차가 크다(범위로만 해석). 일부 조건(2초 간격, JIT 예열 없음)은 5회 중 1회가 다른 실행의 절반으로 양봉 분포 가능성이 있다(원인 미확인).
- 미저장 원인은 §5.1처럼 메커니즘을 분리한 시나리오에서만 판정했다. §2의 saturated 미저장은 메모리 큐 폐기로 **추정**한다(같은 설계 조건이 store_drop에서 확인됨).
- 저장 확인의 DB 읽기는 SDK 내부 스키마에 의존한다. 이를 보완하려고 업로드 서버로 독립 확인했다.
- commit 지연은 identify를 대리값으로 쓴다. track 단독의 commit 시각은 공개 API로 관찰할 수 없다.
- 프로파일은 비율만 유효하며 AOT 상태에서만 수집했다.
- 측정 앱은 SDK 초기화를 `Application`이 아니라 `Activity`에서 한다(측정 앱에만 해당).

### 10.6 한계
- **Galaxy S23 한 대, 조건당 5회** 측정이다. 다른 기기·Android 버전으로 일반화하지 않는다. CPU 클록은 고정하지 못했고 앱 화면은 60Hz로 동작했다.
- 단계별 효과가 작은 개선 2·3은 5회의 편차보다 작아 개별 효과를 확정하지 못했다. 1+2 변형의 1회(2.50ms)는 다른 실행보다 크게 낮아 평균이 아닌 중앙값으로 판단했다.
- 배경 CPU는 무호출 30초 기준값(49~119ms)을 빼서 계산하므로 그 변동이 결과에 섞인다. 호출 스레드를 뺀 모든 스레드(메인 스레드 콜백 포함)의 합이다.
- 개선 1·2의 효과는 쌓인 행 수에 따라 달라질 수 있다(COUNT 비용은 행 수에 비례). 이번 측정의 누적 행은 최대 300 수준이다.
- commit 지연은 identify 대리값이며 메인 Looper 대기가 섞인다.
